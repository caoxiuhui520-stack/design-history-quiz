# 02 · 技术方案与架构设计

> 本文档定义站点的整体架构、技术选型、多人同步协议与关键算法。
> 数据层的字段级规范见 `03-知识库与数据规范.md`。

## 1. 总体架构

站点是**零服务端的纯静态应用**（No-Backend / Serverless-Static），所有能力在浏览器内完成；多人同步通过 WebRTC 或第三方免费实时通道实现，不依赖自建服务器。

```
┌──────────────────────────────────────────────────────────────┐
│                      浏览器运行时（单页应用）                  │
│                                                              │
│  ┌────────────┐   ┌──────────────┐   ┌──────────────────┐   │
```

### 1.1 分层职责

| 层 | 职责 | 关键约束 |
|---|---|---|
| 视图层 | 渲染题目、收集作答、展示反馈 | 不写业务逻辑，只消费 store |
| 状态层 | 会话状态（当前题、作答、进度）、房间状态 | 单一数据源，可持久化子集 |
| 能力层 | 判分、归一化、间隔重复调度 | **纯函数**，无副作用，可单测 |
| 持久化层 | 读写本地存储、版本迁移 | 所有 key 带版本前缀 |
| 同步层 | 房间广播、成员状态同步 | 实现统一接口，可热切换 |

**核心设计原则：判分永远在本地完成，网络只负责「让别人看到我的进度」。** 这样即使同步层完全失效，答题与反馈体验零衰减——这对 2 天工期的项目是最重要的一条风险隔离。

## 2. 技术选型

| 领域 | 选型 | 理由 / 备选 |
|---|---|---|
| 构建工具 | **Vite 5** | 冷启动快、产物小、PWA 插件成熟。备选：无（Vite 已是默认解） |
| 语言 | **TypeScript（strict）** | 题库字段多，类型能在编译期拦住 80% 的数据误用 |
| UI 框架 | **React 18** | 组件化适合答题卡这类高频复用单元；生态最全 |
| 样式 | **手写 CSS + CSS 变量** ⚠️ 原计划 Tailwind | 组件量不大（15 个），砍掉 3 个构建期依赖；产物 CSS 仅 3.3KB gzip |
| 路由 | **自实现 Hash 路由（约 25 行）** ⚠️ 原计划 react-router | 只有 9 个视图，引路由库不划算；Hash 方案天然规避 Pages 的 404 重写问题 |
| 状态管理 | **原生 store + `useSyncExternalStore`** ⚠️ 原计划 Zustand | 全局只有一个 store，为一个 store 引一个库是负收益 |
| 数据校验 | **构建期 `tsc` + 脚本校验（`tools/validate_data.py`）** ⚠️ 原计划 Zod | 校验放在数据侧（V1–V12）比放在运行期更早暴露问题，且零运行时代价 |
| 多人同步 | **PeerJS + mqtt.js**（动态 import） | 两者都只在进入房间时才加载，不影响主包体积 |
| 本地存储 | **localStorage** | 进度数据量小（78 题 × 若干字段）；数据已打包进产物，不需要 IndexedDB 缓存题库 |
| 离线 | ⏳ **待接入** `vite-plugin-pwa` | 当前已可通过「导出进度 + 单文件兜底」覆盖主要离线场景，PWA 排在 M4 |
| 单元测试 | **Vitest** | 与 Vite 同源配置，零额外成本；重点覆盖判分与调度 |
| 代码规范 | **TypeScript strict + 约定**（暂未接 ESLint） | 2 天工期优先保证构建门禁（`tsc --noEmit` + 单测 + 数据校验）有效 |
| CI/CD | **GitHub Actions → Pages** | 推 `main` 自动构建部署，无需本地打包 |

### 2.1 为什么不用「纯单文件 HTML」

单文件方案（一个 `.html` 内联所有 JS/CSS/JSON）开发最快，但有三个硬伤：

1. 78 题 + 知识卡内联后单文件超 300KB，改动一处需整文件重载，git diff 不可读；
2. 多人同步需要引入 WebRTC/MQTT 库，内联后无法按需加载；
3. PWA 离线缓存对单文件不友好。

**但保留单文件方案作为兜底（见 05 章 T5.4）**：D2 导出 `dist-standalone/index.html`，万一 Pages 挂了或考场无网，U 盘双击即可刷题。

## 4. 关键数据流

### 4.1 刷题主流程

```
进入练习
  └─► data.ts 直接使用打包进产物的题库 JSON（零网络请求，无加载态）
        └─► buildPractice 按筛选条件生成题目队列
              └─► 渲染 QuestionCard
                    └─► 用户作答
                          └─► grader.judge()  ← 本地纯函数，零延迟
                                └─► 立即渲染 FeedbackPanel（对错 + 解析）
                                      └─► store 记录作答结果
                                            └─► scheduler 更新该题下次到期时间
```

**关键取舍：题库随 JS 产物一起打包**（Vite 原生 JSON import），而非运行期 fetch。收益：

1. 没有网络请求 → 不会白屏、不会 404、不受 Pages 子路径影响；
2. 数据随 bundle 一起被缓存 → **离线天然可用**，无需 Service Worker 兜底；
3. 代价是改题库需要重新构建 —— 本项目走 Actions 自动构建，成本为零。

实测产物：`index.html 0.6KB` + `CSS 12.3KB` + `JS 245KB`（**gzip 后 89.7KB**，含全部 78 题 + 31 张知识卡 + 14 道大题）。

### 4.2 失败路径

数据已打包，因此**不存在「题库加载失败」这一状态**。唯一的网络依赖是首次下载 bundle：

```
加载 bundle → 成功？ ──是──► 直接渲染（无加载态闪烁）
                │
                否
                ▼
        浏览器原生错误页（此时无任何内容可渲染）
        → 由 PWA 或单文件兜底版覆盖该场景（M4）
```

## 5. 多人同步方案

### 5.1 方案对比

| 方案 | 通道 | 服务端需求 | 可靠性 | 延迟 | 适用规模 |
|---|---|---|---|---|---|
| **A. BroadcastChannel** | 同浏览器多标签 | 无 | 极高 | ~0ms | 1 台设备演示 |
| **B. PeerJS（房主星型）** | WebRTC DataChannel | 仅免费信令 | 中高（受 NAT 影响） | 低 | 2–10 人 ← **默认** |
| **C. MQTT over WSS** | 公共 broker 发布订阅 | 无 | 中（依赖公共 broker） | 中 | 5–50 人 ← **降级** |
| **D. Supabase Realtime** | WebSocket | 免费云项目 | 高 | 中 | 不限 ← **P2 可选** |

**决策**：默认 **B**，失败自动降级 **C**，同设备场景走 **A**。三者实现同一 `SyncAdapter` 接口，房间页顶部显示当前通道，用户可手动切换。

### 5.2 SyncAdapter 接口

```ts
export type PeerId = string;
export type RoomCode = string;   // 6 位大写字母数字，排除易混字符 O/0/I/1

export interface PeerInfo {
  id: PeerId;
  nickname: string;
  avatarSeed: string;
  joinedAt: number;
  isHost: boolean;
}

export interface PeerProgress {
  id: PeerId;
  answered: number;
  correct: number;
  currentIndex: number;
  updatedAt: number;
}

/** 房间事件：所有实现必须原样透传，不得在适配器内解释业务语义 */
export type RoomEvent =
  | { t: 'join';  peer: PeerInfo }
  | { t: 'leave'; id: PeerId }
  | { t: 'progress'; p: PeerProgress }
  | { t: 'host-move'; index: number }      // 房主推进进度（同步刷题模式）
  | { t: 'chat'; from: PeerId; text: string }
  | { t: 'sync-request' }                   // 新成员请求全量快照
  | { t: 'snapshot'; peers: PeerInfo[]; progresses: Record<PeerId, PeerProgress> };

export interface SyncAdapter {
  readonly kind: 'broadcast' | 'peerjs' | 'mqtt' | 'supabase';
  readonly status: 'idle' | 'connecting' | 'online' | 'error';
  createRoom(nickname: string): Promise<RoomCode>;
  joinRoom(code: RoomCode, nickname: string): Promise<void>;
  leave(): Promise<void>;
  send(ev: RoomEvent): void;
  onEvent(cb: (ev: RoomEvent) => void): () => void;
  onStatus(cb: (s: SyncAdapter['status'], err?: Error) => void): () => void;
}
```

### 5.3 房主星型拓扑（方案 B）

```
              ┌─────────────┐
              │   房主(host) │  ← 权威状态持有者
              │  存 peers{}  │
              └──┬───┬───┬──┘
        DataChannel ×3
      ┌──────┘   │   └──────┐
      ▼          ▼          ▼
  成员 A      成员 B      成员 C
 (状态不发A↔B，全部经房主转发)
```

- **房间码生成**：房主 PeerJS id 形如 `dsquiz-h7k2m9x4`，对外只暴露 6 位 `h7k2m9x4` 的**校验片段**，加入时按规则还原完整 id，避免穷举。
- **权威状态**：房主维护 `peers` 与 `progresses`，新成员 `sync-request` 时回发 `snapshot`。
- **心跳**：成员每 10s 发一次 `progress`（带节流，避免刷屏）；房主 30s 未收到则标记离线。
- **房主离开**：广播 `host-move` 语义失效，降级为「自由刷题」模式并在 UI 提示。

### 5.4 消息节流与容量控制

| 参数 | 取值 | 说明 |
|---|---|---|
| 进度广播节流 | ≥ 500ms | 合并高频更新，只发最后一次 |
| 心跳间隔 | 10s | 平衡实时性与流量 |
| 断线判定 | 30s | 未收到心跳即标记离线 |
| 重连退避 | 1s → 2s → 4s → 8s（上限 30s） | 避免公共 broker 被判为滥用 |
| 单条消息上限 | 8KB | 超长内容（如大题作答）不广播 |

### 5.5 隐私边界

房间内**只广播**：昵称、头像种子、作答数量、正确数、当前题号。
**绝不广播**：题目答案明文、小题题干、个人错题明细。

理由：公共 MQTT broker 上的消息是明文且任何人可订阅同名主题，房间安全仅靠房间码。

## 6. 关键算法（概要）

### 6.1 判分引擎

| 题型 | 判定规则 |
|---|---|
| 单选 | 选项集合与答案集合相等 |
| 多选 | 严格集合相等（漏选、多选均判错，与学习通规则一致） |
| 判断 | `T/F` 归一化后相等，兼容「对/错/√/×/true/false」 |
| 填空 | 归一化 → 精确匹配 → 别名匹配 → 编辑距离容错 |

### 6.2 归一化的必要性

题库中同一答案存在多种写法，例如「密斯·凡·德·洛」「密斯・凡・德・洛」（间隔号不同）、「1922」与「一九二二」。归一化管线：

```
原始作答
  ├─ 全角 → 半角（Ａ→A，１→1）
  ├─ 去除空白（含全角空格 U+3000）
  ├─ 去除标点（·・. ，、；：() 《》""'' -—_）
  ├─ 英文统一小写
  ├─ 数字统一（中文数字 → 阿拉伯数字，仅限 0-9999）
  └─ 同义词归一（"格罗皮乌斯" ←→ "格罗佩斯"）
```

完整算法与容错阈值见 `03-知识库与数据规范.md` 第 4 章。

### 6.3 间隔重复调度（Leitner 盒）

每题维护独立记忆状态：

```ts
interface MemoryState {
  box: 0 | 1 | 2 | 3 | 4;   // 0=新题/错题，4=已掌握
  due: number;              // 下次到期时间戳
  streak: number;           // 连续答对次数
  lapses: number;           // 累计答错次数
  lastSeen: number;
}
```

- **答对**：`box + 1`（上限 4），`due = now + BOX_INTERVAL[box]`
- **答错**：`box = 0`，`lapses + 1`，`due = now + 10min`（当天内重现）
- **盒间隔**：`[10min, 1h, 4h, 1d, 3d]`

> 选 Leitner 而非完整 SM-2 的原因：SM-2 的 `ease factor` 需要多轮数据才能收敛，而本项目只有 2 天。Leitner 定长盒对短周期冲刺复习更有效。

**今日复习队列生成优先级**：

```
1. 错题（box=0 且已到期）  ← 最高
2. 到期题（due <= now）
3. 薄弱章节新题（按 stats 正确率升序）
4. 全量随机补充至目标题量
```

## 7. 性能预算

| 指标 | 预算 | 措施 |
|---|---|---|
| 主包 JS（gzip） | < 120KB | PeerJS/MQTT 动态 import；不外引 UI 库 |
| 数据包（gzip） | < 60KB | JSON 字段名精简；去掉冗余显示字段 |
| 首屏可交互 | < 1.5s（4G） | 路由级代码分割；数据加载前渲染骨架屏 |
| 单题切换 | < 16ms | 题目列表预生成；避免答题时重算队列 |
| 内存占用 | < 80MB | 图片一律用 SVG 内联或 emoji，不加载位图 |

## 8. 部署架构

```
本地 push main
   └─► GitHub Actions
         ├─ node 20 setup + npm ci
         ├─ npm run test（判分/调度单测，失败即中断）
         ├─ npm run build（Vite 打包）
         └─ upload-pages-artifact → deploy-pages
               └─► https://<user>.github.io/<repo>/
```

- **缓存策略**：`index.html` 强制 `no-cache`；带 hash 的静态资源 `immutable, max-age=31536000`。
- **数据文件**：带 `schemaVersion` 查询串，题库更新即失效旧缓存。
- 详细步骤与排障见 `06-部署与运维手册.md`。

## 10. 技术决策记录（ADR）

| 决策 | 结论 | 被否方案 | 原因 |
|---|---|---|---|
| 是否自建后端 | 否 | Node + Socket.IO 部署到免费 PaaS | 免费 PaaS 普遍休眠、需保活脚本，2 天内运维成本高于收益 |
| 多人同步默认通道 | WebRTC 房主星型 | 公共 MQTT | 延迟更低、无第三方限流；MQTT 作降级 |
| 路由器 | HashRouter | BrowserRouter | Pages 无法配置服务端重写 |
| 判分位置 | 前端本地 | 服务端判分 | 即时反馈要求零网络往返 |
| 状态管理 | Zustand | Redux Toolkit / Jotai | 体量最小且自带 persist |
| 复习算法 | Leitner 定长盒 | SM-2 | 短周期冲刺场景下收敛更快 |
