# 05 · 开发规范与协作流程

> 目标：2 天内多人（或多人格）协作不互相阻塞，代码风格统一、可回归、可回滚。

---

## 1. 环境准备

### 1.1 前置依赖

| 工具 | 版本 | 说明 |
|---|---|---|
| Node.js | ≥ 20 LTS | 构建与开发服务器 |
| npm | ≥ 10 | 包管理（不引入 pnpm/yarn，减少环境差异） |
| Python | ≥ 3.11 | 仅用于 `tools/` 下的数据脚本 |
| Git | ≥ 2.30 | 版本控制 |

### 1.2 初始化

```bash
git clone <repo-url> design-history-quiz
cd design-history-quiz
npm ci                       # 严格按 lock 文件安装
npm run dev                  # 启动开发服务器 http://localhost:5173
```

### 1.3 常用命令

| 命令 | 作用 |
|---|---|
| `npm run dev` | 本地开发（热更新） |
| `npm run build` | 生产构建到 `dist/` |
| `npm run preview` | 本地预览生产构建产物（**部署前必跑**） |

## 2. Git 工作流

### 2.1 分支模型（极简版）

只有 2 天，不引入复杂分支策略：

```
main ───●────────●────────●────►   ← 始终可部署（Pages 从这里发）
         \      / \      /
          ●───●    ●───●            ← feat/* 短命分支，当天合并
```

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 唯一长期分支，**任何时刻都可上线** | 永久 |
| `feat/<模块>` | 新功能（如 `feat/room-sync`） | ≤ 1 天 |
| `fix/<问题>` | 修 bug（如 `fix/blank-normalize`） | ≤ 数小时 |
| `data/<变更>` | 题库数据修改 | 合并即删 |

**规则**：`main` 上禁止直接提交功能代码；数据修正可直接提交（风险低且可回归）。

### 2.2 提交信息规范（Conventional Commits）

```
<type>(<scope>): <简述>
```

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `data` | 题库/知识库数据变更 |
| `docs` | 文档 |
| `style` | 样式调整（不影响逻辑） |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 构建/依赖/配置 |

示例：

```
feat(practice): 支持填空题多空输入与逐空判定
fix(grader): 修正中文数字与阿拉伯数字互转导致的误判
data: 修正 hw1-q15 克莱斯勒大厦设计者
docs(tech): 补充同步协议的消息节流参数
```

### 2.3 合并前检查清单

- [ ] `npm run test` 通过
- [ ] `npm run lint` 无 error
- [ ] `npm run data:validate` 通过（若动过 `data/`）
- [ ] `npm run preview` 本地跑通该功能
- [ ] 375px 与 1440px 两种宽度都手动看过
- [ ] 若改了数据结构，已提升 `schemaVersion` 或 `dataVersion`

## 3. 代码规范

### 3.1 通用

| 规则 | 说明 |
|---|---|
| TypeScript strict | `strict: true`，禁止 `any`（必要时用 `unknown` + 类型守卫） |
| 命名 | 文件 `kebab-case.ts`；组件 `PascalCase.tsx`；函数/变量 `camelCase`；常量 `UPPER_SNAKE` |
| 导出 | 优先具名导出，避免 `export default`（利于重构与跳转） |
| 副作用 | `core/` 与 `sync/` 内不得直接操作 DOM 或 `window`（除 `localStorage` 封装） |
| 字符串 | 界面文案集中放在 `src/i18n/zh.ts`，**不硬编码在组件里**（便于统一改文案） |
| 魔法数 | 时间间隔、阈值等提取为具名常量 |

### 3.2 组件规范

```tsx
// 组件文件结构固定为四段：类型 → 常量 → 组件 → 子组件
type Props = {
  question: Question;
  onSubmit: (answer: string[]) => void;
};

const OPTION_LETTERS = ['A', 'B', 'C', 'D', 'E'] as const;

export function QuestionCard({ question, onSubmit }: Props) { /* ... */ }

function OptionRow() { /* ... */ }
```

| 规则 | 说明 |
|---|---|
| 长度 | 单组件文件 ≤ 200 行，超出则拆 |
| Props | 只传必要数据，不传整个 store |
| 状态 | 组件内部状态用 `useState`；跨页面状态才进 Zustand |
| 副作用 | 数据加载等副作用集中到自定义 hook（`useQuestions()`） |
| 样式 | 一律 Tailwind 原子类；不写独立 `.css` 文件（仅 `index.css` 放全局变量） |

### 3.3 关键模块的特殊要求

| 模块 | 要求 |
|---|---|
| `core/grader.ts` | **纯函数**，无 IO；每个题型一个策略函数；必须 100% 分支覆盖 |
| `core/normalize.ts` | 纯函数；所有归一化规则以表格形式在文件头注释中列明 |
| `core/scheduler.ts` | 时间通过参数注入（`now: number`），**不直接调 `Date.now()`**，否则无法测试 |
| `sync/*.ts` | 实现同一 `SyncAdapter` 接口；不得在适配器内解释业务语义 |

### 3.4 注释规范

只解释**为什么**，不复述**是什么**：

```ts
// ✅ 好的注释：解释反直觉的原因
// 多选题采用严格集合相等，与学习通判定规则一致（漏选、多选均判错），
// 因此这里不能用「包含」判断。
const isCorrect = ansSet.size === keySet.size && [...ansSet].every(k => keySet.has(k));

// ❌ 差的注释：复述代码
// 比较两个集合
```

## 4. 测试策略

2 天工期，测试只投在**错了会直接导致复习出错**的地方。

### 4.1 必须测试（P0）

| 模块 | 用例要点 |
|---|---|
| `normalize` | 全角/半角、间隔号、空格、标点、中文数字、大小写 |
| `grader.single` | 正确、错误、空选 |
| `grader.multiple` | 全对、漏选、多选、顺序打乱后仍判对 |
| `grader.judge` | T/F 各写法（对/错/√/×/true/false） |
| `grader.blank` | 多空全对、部分对、空格差异、标点差异、别名命中、模糊阈值 |
| `scheduler` | 答对升盒、答错回盒、到期计算、队列优先级 |

### 4.2 数据回归测试

对全部 78 题跑一次「用标准答案作答 → 必须全部判对」的回归：

```ts
test('标准答案自测：78 题全部应判为正确', () => {
  for (const q of questions) {
    const key = q.answer.value;
    const res = judge(q, key);
    expect(res.correct, `${q.id} 用标准答案却判错`).toBe(true);
  }
});
```

这条测试是本项目**性价比最高的一条**——它同时验证了数据和判分逻辑。

### 4.3 可以不做

E2E（Playwright）、视觉回归、性能基准。理由：工期不足，且阶段五有手工回归清单兜底。

## 6. 协作约定

| 约定 | 说明 |
|---|---|
| 接口先定 | `sync/types.ts` 由一人先写定，其他人按接口实现，避免并行开发互相覆盖 |
| 数据冻结 | `data/` 在 M0 后即冻结，后续只接受「纠错」类修改，避免判分基准漂移 |
| 功能冻结 | D1 24:00 后只修 bug 不加功能 |
| 每日同步 | D0/D1 各一次 5 分钟对齐：谁在改哪个文件、有无阻塞 |
| 冲突处理 | 同一文件尽量只由一人负责；`data/*.json` 冲突时以 `parse_bank.py` 重新生成为准 |

## 7. 环境与配置

| 变量 | 用途 | 默认值 |
|---|---|---|
| `VITE_BASE` | Pages 子路径（如 `/design-history-quiz/`） | `/` |
| `VITE_DATA_BASE` | 数据文件目录 | `${BASE}data/` |
| `VITE_SYNC_CHANNEL` | 默认同步通道 | `peerjs` |
| `VITE_MQTT_URL` | MQTT broker 地址 | `wss://broker.emqx.io:8084/mqtt` |

`.env.local` 用于本地覆盖；**不得把任何密钥写入仓库**。当前方案无密钥需求（这也是选择零服务端架构的一个附带好处）。

## 8. 兜底与回滚

| 场景 | 动作 |
|---|---|
| 线上出现严重 bug | `git revert <commit>` 后推送，Actions 自动重新部署（回滚 < 3 分钟） |
| Pages 整体不可用 | 使用 `dist-standalone/index.html` 单文件版本（U 盘 / 微信发送） |
| 数据出错 | 改 `data/` → 校验 → 提升 `dataVersion` → 推送 |
| 依赖装不上 | `npm ci` 失败时删 `node_modules` 重试；仍失败则用已构建的 `dist/` 直接部署 |
